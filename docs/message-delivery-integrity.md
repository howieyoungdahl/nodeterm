# Message delivery integrity

The core delivery queue enforces its original deadline before draining and again at the actual send boundary. A delayed timer or slow pane probe cannot extend it. A delivery exception produces `unknown`, because bytes may already have reached the composer. It never replays that attempt. Expiry notification and receipt storage survive trace or observer failure. Transient flushes are limited to three delivery attempts, with the existing rate-limit delay and original expiry; queued bodies are capped at 64 KiB.

The optional `QueuedDeliveryRequest.message` envelope binds stable message and action IDs to a task, assignment ID/epoch, exact recipient actor, and contract/policy references. `createDeliveryQueue` accepts an injected `validateAssignment` adapter. It must read the canonical assignment authority, compare every binding, and return an explicit `{ok, code}`. Missing or failed validation rejects identified requests. Validation runs at admission, queued delivery, immediately before sending inside the node lock, and recipient acknowledgment. It does not replace creator, project, cold-session, or pane guards. A successful validation is a snapshot, not a lock across the external provider effect.

The process-local receipt cache stores at most 200 identities and hashes, without message bodies or a second task ledger. Concurrent retries of one ID share an outcome; changed payloads conflict, as does reusing an action ID under another message ID. Unexpired receipts are never evicted for capacity. Identities expire within five minutes, and retries cannot renew them. A new process has neither queued payloads nor old receipts; a missing receipt is `unknown`, never proof that replay is safe.

`message.status` distinguishes `queued`, transport `delivered`, recipient `acknowledged`, work `accepted`, `expired`, `unknown`, and `rejected`. Transport delivery still means a verified target turn was observed. That hook is uncorrelated activity and cannot prove acknowledgment, work acceptance, or completion. `messages.acknowledge` is an integration seam that must only be called after authenticating a message-specific recipient receipt. Assignment validation alone does not authenticate its caller. Accepted work still needs separate evidence adjudication before completion.

Both Desktop and Server use the queue builder and send-boundary callback. Their existing control/IPC request shapes remain legacy and uncorrelated; a caller must explicitly supply the new envelope and canonical adapter to opt in. The command parser, capability negotiation, authenticated recipient receipt adapter, durable intent reconciliation, and direct-delivery ID propagation still need integration. Until then, legacy requests gain the queue recovery fixes but do not gain assignment fencing or duplicate detection. No application install or live restart is part of this source change. Mobile is not a sender on this path; a mobile-created target uses the same core checks. Canvas and board require no separate mutation or badge for this change.

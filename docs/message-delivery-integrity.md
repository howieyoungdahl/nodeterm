# Message delivery integrity

The core delivery queue enforces its original deadline before draining and again at the actual send boundary. A delayed timer or slow pane probe cannot extend it. A delivery exception produces `unknown`, because bytes may already have reached the composer. It never replays that attempt. Expiry notification and receipt storage survive trace or observer failure. Transient flushes are limited to three delivery attempts, with the existing rate-limit delay and original expiry; queued bodies are capped at 64 KiB.

The optional `QueuedDeliveryRequest.message` envelope binds stable message and action IDs to a task, assignment ID/epoch, exact recipient actor, and contract/policy references. `createDeliveryQueue` accepts an injected `validateAssignment` adapter. It must read the canonical assignment authority, compare every binding, and return an explicit `{ok, code}`. Missing or failed validation rejects identified requests. Validation runs at admission, queued delivery, immediately before sending inside the node lock, and recipient acknowledgment. It does not replace creator, project, cold-session, or pane guards. A successful validation is a snapshot, not a lock across the external provider effect.

The process-local receipt cache stores at most 200 identities and hashes, without message bodies or a second task ledger. Concurrent retries of one ID share an outcome; changed payloads conflict, as does reusing an action ID under another message ID. Unexpired receipts are never evicted for capacity. Identities expire within five minutes, and retries cannot renew them. A new process has neither queued payloads nor old receipts; a missing receipt is `unknown`, never proof that replay is safe.

`message.status` distinguishes `queued`, transport `delivered`, recipient `acknowledged`, work `accepted`, `expired`, `unknown`, and `rejected`. Transport delivery still means a verified target turn was observed. That hook is uncorrelated activity and cannot prove acknowledgment, work acceptance, or completion. `messages.acknowledge` now refuses without a host authenticator, compares all six recipient actor fields, revalidates the canonical assignment, and rechecks authenticated incarnation and TTL before recording receipt. `acknowledgeReceipt` takes only source/message/action IDs from the app-authored envelope, using the existing cache's assignment rather than caller-edited claims or a reconstructed body. Assignment validation alone does not authenticate its caller. Accepted work still needs separate evidence adjudication before completion.

## Host consumer boundary (local prototype)

Both actual shells construct the canonical validator and register strict `/control/message-deliver`, `/control/message-receipt`, and `/control/message-ack` routes when their control runtime is enabled. Server canvas control remains off by default and keeps its existing edition refusal while off. These routes require the existing app bearer and verified node token before their host handler. A separate `X-Nodeterm-Message-Credential` is passed only to the message authenticator, never forwarded to renderer/legacy handlers, envelopes, traces, or the canonical subprocess. An operator's browser session is not an automatic-agent principal. A node token alone proves neither the exact session/incarnation nor an issuing task's authority.

Canonical validation is configured explicitly at host startup with **all four** environment values: `NODETERM_ASSIGNMENT_PYTHON` (absolute interpreter), `NODETERM_ASSIGNMENT_MODULE` (absolute D15 `ledger.py`), `NODETERM_ASSIGNMENT_SHA256` (pinned source digest), and `NODETERM_ASSIGNMENT_LEDGER` (absolute registry). Server embedding can supply the equivalent `assignmentAuthority` config. There are no default paths or message-supplied paths. The fixed isolated Python invocation calls the existing public `assignment_validate` API, compares the complete returned binding including assignment ID, strips inherited credentials, and bounds runtime/output. Conformance evidence must identify the explicitly selected producer source and its SHA-256 digest; this repository does not prescribe a private source checkout. Reads use D15's existing cooperative sibling lock and make no canonical document mutation; both files must already exist on entry. This does not provide hostile same-user isolation or an atomic lock across provider effects.

The host's `MessageControlRuntime` must authenticate the exact actor, resolve an immutable **already-issued** message by stable message/action ID while validating issuer read authority, and claim the attempt in the issuer's **existing durable intent substrate** before a possible send. Its separate `validateIssuer` must freshly resolve the issuer's assignment/incarnation, contract/policy and permission for the exact action/recipient; a durable claim does not imply any of these. Exact six-field issuer authentication and current authority run again after lookup, around claim and at the actual node-locked send boundary. The bounded queued entry retains that host-only guard closure (not serialized credentials), so queued flushes revalidate the issuer too. A replaced/transferred issuer after claim gives UNKNOWN, never a refund or another claim/send; duplicate requests retain the original cached outcome even if action authority is subsequently revoked. These are cooperative snapshots, not atomic cross-authority locks. This code creates no issuer, credentials, IDs, assignment epoch, second authority ledger, or privileged broker. Immediate delivery, busy admission, flush, and retries share the existing deduplication receipt. Missing/prior-attempt uncertainty is `unknown`, not replay permission; duplicate requests do not claim or send again. A receiver ACK supplies `source_node`, `message_id`, `action_id`, and `status` (`acknowledged` or `accepted`); the sender's receipt query supplies its issued IDs. Neither asks the renderer to authenticate an agent.

**Neither real shell supplies that runtime.** All three registered routes therefore visibly return `message-principal-and-issuer-adapter-unavailable` with “Do not retry,” even with canonical validation configured. Injected-runtime registered HTTP tests prove consumer behavior, not an installed authenticator or issuer/kernel adapter. The qualified credential lifecycle, issuer-to-existing-action claim adapter, recipient client ACK protocol/capability negotiation, restart reconciliation and real agent/device acceptance remain unfinished. No configuration or live activation was performed.

Legacy `send`/`reply`/`notify` and renderer IPC stay explicitly uncorrelated; they gain queue recovery but not assignment fencing or duplicate detection. Identity fields on those legacy boundaries are rejected rather than silently discarded. Only trusted issued `send`/`reply` records are eligible for the new route; no identified `notify` producer is implemented. Mobile is not a sender on this path, and Canvas/board gain no invented completion badge.

## External canonical conformance fixture

The public generic adapter and registered-route tests run without a separate authority source. Actual canonical conformance additionally requires **both** `NODETERM_TEST_ASSIGNMENT_MODULE` and `NODETERM_TEST_ASSIGNMENT_PRODUCER`, each an absolute path to an operator-selected Python file. Neither configured means the two conformance cases are explicitly skipped; partial or relative configuration fails rather than silently reducing coverage. The producer belongs with its authority implementation, not this public repository. Its canonical role and root identities must not be renamed to resemble generic test data.

The test runs `/usr/bin/python3 -I -B <producer> <module> <output-ledger>` with a five-second timeout and a minimal locale-only environment. The output path is inside a newly created disposable test directory, never an existing live registry. The producer must call the selected module's canonical enrollment APIs and produce its ordinary ledger plus sibling lock. It must not discover ambient sources, invoke providers, or reconstruct a hand-authored substitute ledger. The selected module is SHA-256 pinned by the validator before use; retain source and producer digests with the conformance receipt.

The public consumer binding is task `task`, assignment `assignment-task`, epoch `1`; actor fields are agent/node `target`, pane `%1`, session `session-target`, incarnation `incarnation-1`, provider `claude`. Contract and policy references use `/contract` and `/policy` with 64-character `a` and `b` SHA-256 fixture values respectively. The external producer must enroll that binding through the real API, including whatever canonical parent enrollment its implementation requires. These references are synthetic identity-comparison fixtures, not claims of live authority or existing contract files.

Run the actual suites with both paths explicitly selected:

```sh
NODETERM_TEST_ASSIGNMENT_MODULE=/absolute/authority/ledger.py \
NODETERM_TEST_ASSIGNMENT_PRODUCER=/absolute/authority/message-fixture.py \
  npx vitest run src/core/agents/canonical-assignment.test.ts src/core/agents/message-control.test.ts
```

The unchanged assertions cover exact bindings, stale epochs/actors/references, registered delivery and acknowledgment, and unchanged canonical bytes. Passing generic fixtures is not actual-producer conformance, and conformance is not live authenticator, issuer, agent, or device acceptance.
